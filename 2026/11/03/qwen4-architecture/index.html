Qwen4 架构全解：把参数从显存里搬出去

发表于2026-11-03|更新于2026-11-03|AIDeep Learning

截至今天，Qwen4 家族的权重一个都没放出来。云栖大会上说的「11 月第一周」，到现在还停在「即将」。

但 Qwen4 的架构，其实已经在 Hugging Face 上躺了两个多月。

8 月 27 日，Qwen 开源了 Qwen3.8-Flash-Next，官方博客里有一句话说得非常直白：它是 “an early preview of the architecture used in Qwen4”。这和当年 Qwen3-Next 之于 Qwen3.5 是同一套玩法——先把骨架放出来让社区啃，再往上长整代模型。

所以这篇不是「发布解读」，而是照着 config 和官方技术博客，把 Qwen4 的骨架拆一遍。好消息是这份骨架足够硬：config.json 里每个超参都是真的，算出来的参数量和官方口径对得上；坏消息是 Max、Plus、Flash 三档的规格一个字没公布，任何声称「Qwen4-Max 有 X 万亿参数」的说法都还是猜的。

先划一下证据边界

这两年读模型架构，最容易踩的坑是把二手的推断当一手规格。这篇会反复回到三份材料：

材料 性质 能信到什么程度
Qwen3.8-Flash-Next 的 config.json 与权重 官方，已开源 硬事实，可复算
阿里云官方博客《A New Architecture, Towards Ultimate Cost-Efficiency》 官方 硬事实，但有选择性披露
同仓库的 tech report 官方 硬事实
HF Transformers 里的 qwen4_exp 文档 官方 下一代实现的另一条分支，不等于最终形态
llama.cpp / vLLM 里合入的 Qwen4 图执行补丁 第三方 只到「算子契约」级别，权重逻辑没给
Arena 上代号 Kalmia 的匿名模型、X 上的本地跑分 社区 传闻，本文只在最后提一句

记住一个数字关系，后面所有困惑都能解开：125B + 51B = 176B。有的拆解文章说这个预览模型是 176B 总参，有的说 125B，其实是在算不算那 51B 查表参数。

规格速览

N-gram 查表参数 51B（不入矩阵乘）

对照一下上一代的位置感：Qwen3.8-27B 是 64 层、hidden 5120 的稠密模型，这个 125B 的 MoE 每 token 只动用 6B——参数是它的 4.6 倍，算力只有它的零头。官方给的口径是训练成本约为 Qwen3.7-Plus 的 1/9，能力还更强。

上面这些数字不用信我，config.json 是公开的，五行代码就能自己数一遍：

三条扩容轴，一条搬运轴

把官方的四个改动点（attention / residual / embedding / optimization）重新排一下，会发现它们各自解决的是完全不同的问题：

  1. QSA：减少「看多少」——把注意力的检索范围从全序列压到 2048 个 token；
  2. GDN：减少「记多少」——把历史压进固定大小的状态，KV cache 只存在于 1/4 的层；
  3. Gated Residual：改善「怎么传」——不省算力，省的是深层网络里的信号衰减；
  4. N-gram 查表：增加「记了什么」——用几乎零 FLOPs 的方式扩容，代价是内存。

前三条是省，第四条是加。而第四条才是这一代真正的分水岭：它第一次把「模型容量」和「HBM 容量」解耦了。

QSA：把 indexer 也一起压掉

先看稀疏注意力这两年走过的路。

DeepSeek 在 V3.2 里提出的 DSA 是 token 级的：用一个小号 indexer 给每个历史 token 打分，选出 top-k 再算注意力。注意力本身的成本从 $O(n^2)$ 掉到了 $O(nk)$，但 indexer 自己还是要把 $n$ 个位置全部打分一遍。上下文到 1M，这笔「索引税」就不再是零头了。

Qwen 的 QSA（Qwen Sparse Attention）的做法是：连索引的粒度也一起压。

对应到 config 就是四个数：indexer_compress_ratio = 4、indexer_budget = 2048、indexer_n_heads = 4、indexer_kv_heads = 1。在 1M 上下文下，每个 QSA 层实际只 attend 2048 个 token——**全序列的 0.2%**。

这里有一个设计选择值得单独说：Qwen 明确不走跨层索引复用（IndexCache 那条路），而是每一层独立做序列压缩。理由写在博客里，翻译过来是：在 GDN 和注意力交替的混合架构里，层与层之间的表示差异太大，「相邻层选出同一批位置」这个假设站不住。代价是每层都要跑一次 indexer，换来的是不依赖跨层相似性的鲁棒性。

官方给的数是：1M 上下文下，QSA 的 attention kernel 在 prefill 上最高 7.6×、decode 上 4.9× 的加速；在 90% 前缀缓存命中这种贴近线上服务的设定下，prefill 吞吐是 Qwen3.7-Plus 的 8.6 倍。

最后那个数字比前面两个更值得关注——它说明收益不只来自算法，还来自和 prefix caching 的配合。

GDN + QSA：3:1 的分工

48 层里，每 4 层是一个循环：三层 GDN，一层 QSA。layer_types 数组写死了这个节奏。

GDN（Gated DeltaNet） 是线性注意力家族里的一员，用 delta rule 把历史压进一个固定大小的矩阵状态。它的关键性质是：状态大小与上下文长度无关。按 config 算一下这个状态有多大：

$$48 \times 128 \times 128 \times 36\ \text{层} \approx 2.8\times10^{7}\ \text{个 fp32} \approx 113\ \text{MB}$$

113MB，固定值，1K 上下文和 1M 上下文一样大。

QSA 层 则保留真正的 KV cache。每 token 每层的 KV 是 2 头 × 256 维 × 2(K,V) × 2 字节 = 2KB，12 层加起来 24KB/token：

上下文 QSA 层 KV cache
32K 0.8 GB
262K 6.3 GB
1M 24.6 GB

换成 48 层全注意力的模型，这三个数要乘 4。这就是「3:1」的算术意义：绝大多数层用常数内存记住历史，少数层用线性内存精确定位。

官方那句话总结得比我说得好：

GDN 高效地「记住」，QSA 精确地「检索」。

值得注意的是这个比例本身。Qwen3-Next 时代就是 3:1，一路沿用到 3.5/3.6/3.7/3.8，到 Flash-Next 没动。这个比例大概率已经过了消融验证，属于「不要再调」的那类超参——同时也意味着，如果 Qwen4-Max 是同一个骨架长大，那它的「记忆/检索」配比大概率也不会变。

Gated Residual：把一条残差流劈成四条

残差连接是 2016 年到现在唯一没被真正重写过的结构。所有层不停地往同一条残差流里读和写，网络一深，早期特征就被反复稀释。

Gated Residual（GR）做两件事：

  • 学 Hyper-Connections，把残差流从 1 条扩成 4 条并行分支（config 里的 hc_count=4）；
  • 学 GatedNorm，在读写的时候加逐元素的、依赖当前内容的动态门。

写成式子大概是这样（我只保留主干）：

$$\mathbf{x}_{b}^{\ell+1} = g_{b}^{\text{read}}(\mathbf{h}_{\ell})\odot \mathbf{x}_{b}^{\ell} + g_{b}^{\text{write}}(\mathbf{h}_{\ell})\odot \mathrm{Layer}_{\ell}(\mathbf{h}_{\ell})$$

有意思的是 Qwen 对 Hyper-Connections 做的减法：原版里分支之间还有一层混合矩阵 $B$，Qwen 直接把它删了。理由是——只要读门和写门足够表达，分支混合带来的收益不显著，反而多一次访存、多一个不稳定源。这和 DeepSeek-V4 的 mHC 恰好相反：DeepSeek 保留混合矩阵，但把它约束到双随机矩阵流形上换数值稳定；Qwen 干脆不要这个矩阵。

同一个问题，两种解法，一家用数学约束，一家用结构简化。

官方还披露了一个挺有意思的观测：四条分支里有一条会自发变成远程通路，从第一个注意力层一直连到中后段的大部分层。没人设计它，是训练自己长出来的。

工程上还有两点：门本身抑制了激活离群值，训练更稳；残差状态可以存成 FP8，访存再省一半。

N-gram：51B 参数住在 CPU 内存里

这是整篇文章里最值得慢慢看的部分，因为它改的是「模型参数必须待在显存里」这条十几年没动过的前提。

做法：标准 embedding 是一个 token 查一行。N-gram embedding 用当前 token 加前两个 token 组成的三元组去查表（ngram_size = 3），给常见短语和局部模式额外的表示。

地址怎么算：不是查一张大表，而是 16 张子表（8 张给 bigram，8 张给 trigram，heads_per_ngram = 8）。每张子表用一个混合哈希定位：

$$h = \Big(\bigoplus_{i=0}^{n-1}\big(x_{t-i}\cdot m_i\big)\Big) \bmod 2^{64} \qquad \text{row} = h \bmod p_h$$

$m_i$ 是模型自己的层内乘子，$p_h$ 是这张子表的局部词表大小。序列开头或遇到 EOS 时，缺失的前驱会被补成 EOS id。含义很清楚：地址只依赖上下文本身，可以在生成开始前批量算好——这正是它能被异步预取的前提。

为什么能省：地址在 prefill 一开始就能全部算出来，于是这张表可以放在主机内存（DDR5），用异步预取和 GPU 计算重叠。官方口径是「不永久占用显存」。

到底多大：ngram_vocab_size_base = 20000000，ple_embed_dim = 2560，乘起来：

$$2.0\times10^{7} \times 2560 \approx 5.12\times10^{10}$$

正好是官方说的 51B。按不同精度折算：

存储 体积 能不能塞进单机
bf16 ~102 GB 要 8 通道以上的服务器内存
INT8 ~51 GB 工作站可以
IQ4_NL（GGUF 里的实际格式） ~26 GB 单条 64G 内存条就够

社区里流传的「51GB 表文件」，对应的就是 INT8。

放置位置：ple_layer_ids = [2]——只有第 3 层（0-based 的 2）挂了这张表，位置很靠前，紧跟在两层 GDN 之后。官方说这是一个「大规模局部模式记忆」，挂在开头最划算。

工程后果，我觉得比架构本身更重要：

  • 带宽几乎不是问题。 每 token 只取 16 行 × 2560 维，bf16 下 80KB、int4 下 20KB。batch 64、100 tok/s 的场景也就百来 MB/s，PCIe 完全无感。
  • 延迟才是问题。 每个 token 都要一次跨总线的随机访存，预取晚了就是一个 stall。这是「查表」和「算矩阵」在工程上的根本差异——前者对延迟敏感，后者对带宽敏感。
  • 容量变成硬门槛。 26GB 的表意味着消费级显卡 + 64G 内存是这条路的入场券，而不是「跑得动跑不动」的问题。

顺带说一句：这条路 DeepSeek 在 V4 里点过名但没落地（Engram，条件记忆），理由是留给下一代。Qwen 先把它做进了开源权重。2026 年两家在「记忆」这件事上分道了：一家继续在注意力内部压缩，一家把记忆搬到显存外面。

MoE：512 个 640 宽的专家

细粒度 MoE 大家都在做，但 Qwen 这里走得比多数人更极端：

项 数值 对比
专家数 512 DeepSeek-V4 是 256/384
每 token 激活 10 6
专家中间维 640 常见是 1408–2048
共享专家 1（同样 640 宽） 1

把参数量算一遍，验证一下 125B 是怎么来的：

$$512 \times 3 \times 2560 \times 640 \approx 2.52\ \text{B / 层}$$

48 层全算 MoE 的话是 121B，加上共享专家（约 0.24B）、注意力和 GDN（约 1.7B 和 0.4B）、词表 embedding（约 0.64B），加起来 124B 出头——和 125B 对得上。

每 token 激活的这 6B 也可以验：10 个专家 49M/层 × 48 层 ≈ 2.4B，加共享专家 0.24B、注意力 0.4B、GDN 约 1.7B、词表 embedding 0.64B，合计 5.4B。剩下 0.6B 的差额，大概落在我没逐个数的门控和 norm 上。手算到 5B 量级、官方说 6B，量级对得上。

为什么专家要又小又多：单个专家越窄，路由器的分辨率就越高，专家的分工越细。代价是每 token 要 gather 10 份专家权重，通信和访存的开销都被放大。这套设计只有在 EP（专家并行）+ 高带宽互联下才成立——所以 Qwen 的路线图里始终有自研芯片的位置。

稳定性上沿用了 Qwen3.5 以来的一整套：零中心 RMSNorm 且 norm 权重也吃 weight decay、注意力输出门控、MoE 路由器归一化初始化。

训练：Muon、去掉 warmup、重拟合 scaling law

优化器换成了 Muon，但真正有意思的是三个实现细节，官方说这才是决定成败的地方：

  1. 正交化精度。Newton-Schulz 迭代的步数和系数要重新调。
  2. 哪些参数给 Muon。注意力、GDN、MoE 专家的主权重走 Muon；embedding、MoE 路由器、GR 的低秩参数继续走 AdamW。
  3. 融合矩阵要先拆开。QKV、SwiGLU、GDN 的各种投影在实现里是拼在一起的，Muon 要求按「独立的线性变换」分别正交化，所以得先拆再算。

还有一个反直觉的结论：Batch Size Warmup 可以不要。

从小 batch 慢慢爬到目标 batch，是过去几年大规模训练的标配操作。Qwen 的结论是它不仅没用，还多花 18.8% 的优化步数——因为前期的步数全浪费在小 batch 上了。新 recipe 直接上目标 batch，配合更大学习率。

这是「架构换了，老经验就得重验」的典型例子。scaling law 也重拟合了一遍，结论是新架构能稳定吃更大的 LR 和 batch。

推理侧的经济账

架构讲完，看钱。qwen3.8-flash 的官方定价是 每百万输入 token 0.16 美元、输出 0.47 美元。

这个价位对应的能力，官方给的对比是「训练成本只有 Qwen3.7-Plus 的 1/9，coding 和办公任务还更强」。落到推理上，能省的地方有三层：

  • 算力：6B 激活，单 token FLOPs 是稠密模型的几十分之一；
  • 显存：KV cache 只存在于 1/4 的层，1M 上下文 24.6GB 而不是 100GB 级；
  • 容量：51B 查表参数不占 HBM，把最贵的那块内存留给 KV cache 和专家。

三条加起来，1M 上下文的单位成本才可能压到这个位置。这也解释了为什么官方敢把「1M 上下文」做成默认值而不是可选项。

27B：能下载的那个

Qwen4 四档里，27B 是唯一明确承诺开源的。而在它发布之前，社区已经从 llama.cpp 的一个补丁里把配置推出来了：

维度 推断值
类型 严格稠密（PR 里写死是 dense）
Hidden 5120
骨架 3:1 的 GDN + 注意力，第 4 层换成 QSA
残差 HC4
MTP 有，draft = 4
原生上下文 未公布

注意 PR 自己的免责声明：它只验证了配置和算子契约，真实的 QSA 权重并没有提供。所以这张表是「架构能跑通」的证据，不是规格书。

但它确认了一件重要的事：GDN 的头配置（QK 16 头、V 48 头、head_dim 128）和 Flash-Next 完全一致。骨架确实在往下传，27B 不是另起一套。

和 DeepSeek-V4 摆在一起看

把这两家的选择并排放，会发现它们在同一个问题上给出了方向相反、但都能自洽的答案：

维度 DeepSeek-V4 Qwen4（预览）
长的部分怎么处理 CSA + HCA 两种压缩注意力交替 GDN + QSA，3:1 混合
稀疏检索的粒度 压缩块，再做 token 级 top-k micro-block（4 token）级
残差怎么稳 mHC，保留混合矩阵但约束到双随机矩阵流形 GR，砍掉混合矩阵，靠门
容量往哪扩 Engram 点名留给下一代 N-gram 查表，51B 已落地
优化器 Muon Muon
上下文 1M 原生 262K 原生 / YaRN 1M

有意思的是第三行和第四行正好互为镜像：DeepSeek 在残差上加数学约束、在记忆上按兵不动；Qwen 在残差上做减法、在记忆上先落一子。两家都用了 Muon，说明这个优化器在 2026 年已经从「Kimi 的独门配方」变成了行业默认。

如果只记一句话：DeepSeek 把稀疏性花在注意力内部，Qwen 把稀疏性花在显存外面。

还没答案的问题

写到这儿，能确认的都确认完了。剩下的是真问题，不是我懒得查：

Qwen4-Max 会有多大，会开源吗。 Max 这条线从 2025 年 9 月起就是 API-only，没有一次例外。云栖的公开承诺只覆盖到「27B 优先开源」，没有一句话说 Max 会给权重。把 5–10 万亿参数的路线图往 Qwen4 头上套是错的——那个数字说的是 Qwen4.5 和 Qwen5。

125B 的比例能不能外推。 专家粒度、GDN:QSA 的 3:1、indexer 预算 2048，这些在 Flash 档验证过，但 Max 档是不是同一套配比，没人知道。稀疏度和模型宽度之间不是线性关系。

查表的 scaling 上限在哪。 这是我最想在技术报告里看到的章节。查表提供的是「记忆」，不是「组合泛化」。社区测试者在 X 上记录过一个现象：这个预览模型在复杂交互逻辑的代码任务上会翻车，五次都没写出能跑的循环，而稠密的 27B 一次就过。这个观察样本太小，不能当结论，但它指出的方向很明确——用内存换来的容量，和用算力换来的容量，不是同一种东西。51B 的表能扩到 200B 吗？扩到哪一步开始不划算？

1M 上下文的真实 recall。 论文给的是 kernel 加速比，不是检索准确率。只看 0.2% 的 token，长文档里的「大海捞针」还剩几根，得等第三方评测。

总结

把 Qwen4 的架构放回这两年的路线里看，主线其实只有一句话：

不要问模型有多大，要问哪些参数必须待在 HBM 里。

125B 主模型 + 51B 查表的组合，第一次把模型拆成了「必须算的」和「只需要查的」两类，然后给它们安排了两种不同的内存。配上 3:1 的 GDN/QSA 混合和 4 分支残差，最终形态是：容量在涨，单 token 算力在降，长上下文的边际成本在降。

这不像一次「架构创新」，更像一次内存层级的重新分工。真正的创新点不在某一层，而在于它敢把 30% 的参数放到 PCIe 的另一端去。

风险也很清楚：查表的收益依赖命中率和延迟，稀疏检索的收益依赖索引质量，两者都还没有大规模的公开验证。等 27B 的权重下来，这些问号才会有第一个像样的答案——按目前的说法，那是「11 月第一周」的事，也就是这几天。

我会盯着 Hugging Face 的 commit。
